# Lumap 自定义模型供应商运行手册

更新日期：2026-09-30

## 当前演示配置

Lumap 的非敏感默认值为：

- Base URL：`https://api.ikuncode.cc/v1`
- 协议：OpenAI Responses
- 模型：`gpt-5.6-sol`
- 实际生成路由：`https://api.ikuncode.cc/v1/responses`

用户也可以直接填写完整的 `/responses` 地址。应用会保留模型名称原文，不对 `gpt-5.6-sol` 增删前缀或改写。请求使用 Bearer 认证和 `Lumap/0.1.0 (Apple; Education App)` User-Agent。API key 只进入设备 Keychain，不写入代码、文档、日志、SwiftData 或学习数据导出。

对 **`api.ikuncode.cc` + `gpt-5.6-sol` + Responses** 这一确切组合，应用显式发送 `reasoning: {"effort":"low"}` 和 `text: {"verbosity":"low"}`，减少交互生成的等待；其他供应商、模型和协议不会被加入这些参数。官方文档列出的 GPT-5.6 Sol 默认推理级别是 **medium**，支持 **low**，没有列出 **minimal**；不能因为原请求省略推理参数就声称它使用了 high。`text.verbosity` 设置默认输出详略，具体任务的页数、完整讲稿长度和 JSON 合同仍由提示与校验约束，原输出上限保持不变。参见 [GPT-5.6 Sol 模型文档](https://developers.openai.com/api/docs/models/gpt-5.6-sol) 与 [GPT-5.6 参数指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)。第三方网关的实际执行仍以真实联调为准。

## 已验证的网关状态与分组处理

2026-09-30，账号持有人明确同意把当前演示令牌从 **Codex（0.25x）** 切换到 **Codex-Mixed（0.4x）**，随后已在供应商控制台完成保存。切换后，对 `/v1/responses` 发出的真实 `gpt-5.6-sol` 请求返回 HTTP 200、`status: completed` 和 `Lumap connected`。后续课程规划、学习活动、答案评价与教学讲稿也已使用该模型进行真实生成验证。这是当日的验证结果，可用性和费率仍取决于供应商后续状态。

原分组能读取模型列表，但生成请求出现 `unknown provider` 等错误。因此 Lumap 的 **Test connection** 执行一次最短生成请求，只有收到可解析的模型文本才显示 **Generation verified**。HTTP 503、`Codex group unavailable`、`unknown provider` 或格式无效都会显示 **Configured · generation unavailable**，不会把模型列表可读当作生成成功。

以后需要查看或修改当前令牌分组时，可在控制台按以下路径操作：

1. 进入 **API 密钥**。
2. 打开本次使用的**演示令牌**。
3. 选择 **编辑**。
4. 在 **分组** 中选择 **Codex-Mixed**。
5. 点击 **保存**。

应用本身不操作供应商控制台，也不自动更改分组。上面的分组切换已经得到本次用户授权并完成，无需重复切换。控制台对 Codex-Mixed 的当日说明是 Pro／Plus／Team 混合池，第三方客户端可能没有缓存与 fast，C3 费率为 0.4x。

## 真实检索、课程与学习活动

用户输入学习目标后，应用先通过 DuckDuckGo HTML 搜索与 Wikipedia API 获得公开资料，再读取可访问网页的正文；不是仅把搜索摘要包装成课程。资料保留标题、真实 URL、摘录、抓取时间和应用分配的 `S1…Sn` 引用编号。没有可读资料时显示错误和重试入口，不生成固定的备用课程。

主动选择上传资料后，只用所选资料进行课程编排；资料正文、个人信息与密钥不会成为公开搜索查询。生成请求会把用户选择的摘录及学习背景发送到已配置的模型供应商。来源中的指令被当作不可信文本处理。公开资料可能受登录、反爬和正文质量限制，应用不绕过访问控制。

模型先规划 2–12 个内部学习区块，实际区块数取决于目标范围、已掌握内容、可用时间和理解缺口。规划包含前置依赖、目标、时长、推荐方法和诊断问题，每个区块安排 1–3 种有先后顺序的方法，并包含主动练习。用户逐段进入当前区块；尚未打开的区块会根据实际回答再调整，模型可以改变标题、具体目标、内容重点、时长及方法组合，同时保留区块 ID 与前置依赖。

进入具体方法时，再针对当前区块生成简洁讲解、例题、交互任务、答案标准及引用。方法之间应穿插概念连接、情境决策、回忆、步骤预测、复述等操作，避免把全部内容呈现为纯文本。回答评价依据实际任务与标准生成 0–100 分、具体误区和下一步建议。结构化输出会严格校验，无效结构最多纠正一次；模型明确报告资料不足时立即停止，不要求它补出没有依据的课程。

单次结构化规划、区块调整、活动生成或评价操作使用 **90 秒总时限**，包括最多一次结构修复，超时后显示重试错误。客户端同时设置 URLSession 请求超时和独立墙钟截止时间，避免上游缓慢传输令等待状态一直持续。公开检索是之前独立的步骤，因此“搜索资料到首个活动”的总耗时不等于 90 秒。完整讲稿等其他较长生成保留 180 秒默认时限。活动输出目标压缩为约 450–750 词，并减少无关数组与重复文字；不会用固定样例掩盖请求失败。

当前自适应策略是“模型规划 + 已记录的答题证据 + 前置依赖约束”。推荐会参考已确认兴趣、近期误区、学习时间和各方法的实际表现；这不表示已经训练或部署独立强化学习权重。AR 仍为标注清楚的展示模式。

## 多页课件、完整旁白与错误处理

进入 **Narrated Deck / 讲解课件** 时，应用使用当前主题、课程资料、教学语言和学习背景生成完整教学讲稿。模型回复必须通过 `lumap.narrated-deck.response.v1` 合同校验，包括至少 5 页、连续页码、允许的视觉类型、完整旁白、至少 2 个 Quiz、正确选项和强度范围。Responses 的 `status: incomplete`、Chat 的 `finish_reason: length` 等截断信号会被拒绝，避免把一页或半份讲稿当作成功结果。

远程失败时，当前学习流程显示原因并提供重试，不自动换成无关固定课程；示例预览与真实生成内容应明确区分。成功内容与其来源、主题和学习语言一起缓存，重开同一课程可继续使用已验证内容。

Kokoro 本地旁白与大模型课件生成是两个独立步骤：远程模型生成每页内容与完整讲稿，Kokoro 在设备上把每页旁白转换成音频。播放会播完整段后再进入下一页，Quiz 在页面讲解结束后出现，避免中途截断旁白。完成记录需要全部页面完成播放并回答全部 Quiz；单纯打开播放器不会记为掌握知识。

## 本次真实联调记录

以下是 2026-09-30 的实际 API 结果，不代表对任意主题或任意输入的正确率承诺：

- “想学光合作用”生成 6 个知识节点；“I want to learn eigenvectors in linear algebra”生成 7 个不同节点，各自保留 5 个实际抓取的来源。
- 光合作用的 16 种非 AR 方法均完成生成与结构校验，包括讲解课件的大纲；特征向量额外验证了逐步讲解、回忆卡和剧情模式，共 19 份不同活动。完整多页视频播放器另有专门联调。
- 光合作用的标准答案得 95 分、明显错误答案得 0 分；特征向量对应为 100 与 0 分。低分结果均建议留在当前节点，换用误区诊断。此处验证的是评价链路会根据内容变化，并非评价器准确率基准。
- 两个主题的后续问答及基于园艺兴趣、低分回忆表现和“植物碳来自土壤”误区的 4 条推荐完成真实生成。
- 单独以本地 Morse 时间规则资料生成 6 节点课程，保留唯一上传来源及空公开 URL；自动化网络夹具同时验证资料正文不发往公开搜索服务。

联调中曾出现两次供应商 HTTP 524（其上游 120 秒代理超时），分别发生于模拟活动和评价请求；再次请求均成功。应用显示真实错误并允许重试，已有成功课程仍可从缓存恢复。该问题不能通过把客户端超时继续调高来消除，录制前应检查供应商状态并预留生成时间。

顺序区块更新的后续验证使用了上述特征向量课程的真实评价证据：0 分的理解缺口产生“矩阵以不同方式移动箭头”的修复区块，安排 workedExample、simulation、misconceptionDiagnosis，12 分钟；100 分证据产生“预测特征向量方向与缩放”的迁移区块，安排 workedExample、simulation、transferChallenge，20 分钟。两次调用分别用时 7 秒和 14 秒，区块 ID 与前置依赖均保持不变。这证明调整输入会影响后续目标及方法，并不构成推荐效果的因果评估。

较短活动的并发压力测试中，simulation 用时 45 秒、workedExample 用时 89 秒，visualMap 在 90 秒截止时显示明确超时。应用应按学习顺序生成活动，避免同时请求多个完整活动导致供应商排队。上述是本次实测耗时，不是服务时延承诺；前端须保留进度、停止和重试反馈。

该 visualMap 随后单独重试仍在截止时间附近结束（实测约 91 秒，返回明确超时），所以不能把问题仅归因于并发，也不能宣称当前供应商对所有交互模式都能稳定在 90 秒内完成。此前较长时限的完整模式联调已验证 visualMap 能生成有效内容；新截止时间保证本轮不会无限等待。后续性能工作需结合供应商负载或其支持的推理配置继续验证。

随后在相同模型、网关与课程上下文中加入上述 **low 推理 + low 详略** 参数，单独发起一次 visualMap 生成，实测 **33 秒成功**，返回 7 个概念、6 条连接并通过引用及结构校验。该次生成对应先前两次触及 90 秒截止的交互类型。这个对照支持继续使用显式低推理设置，但样本量为一次，供应商负载也可能变化，不能承诺所有请求固定提速或永久不再超时。

## 演示前检查

1. 在 Settings 确认 Endpoint、Responses、`gpt-5.6-sol`，密钥框留空表示保留 Keychain 中的现有值。
2. 点击 **Test connection**。只有 **Generation verified** 才表示生成链路可用。
3. 输入一个具体主题，等待“搜索资料 → 编排课程 → 生成活动”完成，检查课程目标与来源确实对应输入主题。
4. 尝试另一个主题，检查知识节点、例题和方法内容随之变化；给出一个错误答案，检查反馈指出相应误区，而不是只根据回答长度给分。
5. 打开 Narrated Deck，确认生成多页内容，试听完整页面并完成 Quiz。若网关不可用，保留真实错误状态并重试，不把示例预览录成已完成的实时生成。
6. 录屏不要打开密钥编辑框，不展示供应商令牌值或请求认证头。
